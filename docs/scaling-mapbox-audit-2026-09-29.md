# KEYORA scaling and Mapbox lifecycle audit (2026-09-29)

Branch: `codex/scaling-mapbox-lifecycle`. This report describes source changes and local checks. It does not claim a production load test or live database migration.

## Queries, indexes, and cache

Changed: project map select, POI map select, POI admin select, readable slug lookup, and project route cache hydration. The existing detail query still loads galleries, amenities, plans, fees and unit rows for one selected project. Tours already fetch metadata first and current-scene media through signed URLs; the bundle does not download panorama binary data on map entry. No 360 panorama preloading was added. The project map still loads compact unit rows to preserve the existing per-unit pricing and filter behavior; a server-side price aggregate would be a future reduction.

The existing `(lat, lng)` indexes on each POI table serve the new coordinate filters. Existing `projects.slug` uniqueness and tour foreign-key/order indexes were kept. One new `projects_readable_name_idx` supports the legacy name-only lookup. The developer-suffixed legacy form can still scan on the server. Existing usage/billing indexes and tables were not duplicated. TanStack Query caches stable project-map data for five minutes and POI bounds for one minute (five-minute garbage collection); auth transitions purge cached data. Signed URL TTL remains one hour with a 50-minute cache.

## Request pattern and capacity limits

The map issues one project-list query and only requests POIs when a category is active and the camera is close enough; each selected category produces one bounded query after a settled movement. Opening a project uses the route loader once; opening an offer fetches that project's full details. Opening a tour fetches tour/project metadata and its published scene list, then current-scene media and hotspots through the existing route. Actual count varies with auth/config and tour data. At 100, 500, or 1,000 simultaneous active users, backend query volume scales with each user's initial load and interaction rate; these numbers are **not validated concurrency capacities**. A staging load test with production-like data, Supabase query plans, API metrics and mobile browser memory traces is required before making a capacity claim.

The heaviest remaining payloads are full detail relations for one project, compact unit rows for every map project, and the tour scene metadata list. Admin project/user tables and activity events still need systematic server-side pagination and search. The POI cap can omit crowded results; zooming in narrows the area. The production hard-limit RPC reserves a slot atomically for two minutes; the client releases unused reservations on cancellation/unmount. A failed event write or a Mapbox load exceeding that window still needs staging fault testing. For mobile, inactive train animation stops and custom map layers use the existing inactive/visibility guards, but a retained Mapbox WebGL context consumes GPU memory beside Cesium. Profile low-memory devices before release and provide a memory-pressure fallback if needed.

## Verification

`npm run lint`, `npx tsc --noEmit`, `npm run test:usage-billing`, and `npm run build` passed after the integration correction. The 360 data/viewer, photorealistic and Cesium geodata checks passed on the same branch before that correction; their code paths were unchanged. The production database's `per_tenant_mapbox_load_limits` migration is already applied but its source is absent from current `main`; it must be recovered into version control before a reproducible fresh deployment. The new SQL file in this PR only adds the RLS-aware readable-slug lookup and index. A real browser test should confirm one `mapbox_map_initialized` after the first Satellite load, zero additional events after ten Satellite/3D toggles and pans/zooms, a new event after a genuine reload, and stable Cesium/mobile rendering. RLS, index plans, migration behavior and 100/500/1,000-user performance require staging verification.
